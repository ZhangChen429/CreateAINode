## 二、黄金圈三层详解

### 2.1 WHY层：核心信念（最内圈）

#### 设计哲学的4个支柱

```
支柱1️⃣：社会性（Social Nature）
┌────────────────────────────────────────┐
│ 问题：传统游戏NPC是"孤岛"             │
│ 信念：人是社会动物，NPC也应该是       │
│ 实现：每个NPC属于AttitudeGroup        │
│ 效果：Arasaka守卫自动敌视Militech     │
└────────────────────────────────────────┘

支柱2️⃣：协作性（Cooperation）
┌────────────────────────────────────────┐
│ 问题：NPC各自为战，缺乏配合           │
│ 信念：组织成员会协同作战              │
│ 实现：Squad系统 + Order机制           │
│ 效果：小队成员掩护、侧翼、压制        │
└────────────────────────────────────────┘

支柱3️⃣：叙事性（Narrative-Driven）
┌────────────────────────────────────────┐
│ 问题：场景NPC无法推进剧情             │
│ 信念：场景状态应驱动剧情发展          │
│ 实现：Phase系统 + SceneSolution       │
│ 效果：警报响起，守卫数量从5→15       │
└────────────────────────────────────────┘

支柱4️⃣：持久性（Persistence）
┌────────────────────────────────────────┐
│ 问题：NPC死亡后无限刷新               │
│ 信念：玩家行动应有持久影响            │
│ 实现：PersistencySystem + 死亡计数器  │
│ 效果：清理的据点不会刷新              │
└────────────────────────────────────────┘
```

#### 玩家体验目标（User Experience Goals）

```
目标场景：玩家攻击军事检查站

传统AI行为：
├── ❌ 每个守卫独立反应
├── ❌ 各自寻找掩体
├── ❌ 无组织的射击
└── ❌ 玩家感受："这是一群笨AI"

2077 AI群组行为：
├── ✅ 一人发现，全队警戒（Squad事件广播）
├── ✅ 队长指挥，成员执行（Order系统）
├── ✅ 有人掩护，有人侧翼（战术协同）
├── ✅ 狙击手保持高位（角色分工）
└── ✅ 玩家感受："这是一支训练有素的军队"

WHY的价值体现：
→ 沉浸感：相信这是真实的军事检查站
→ 挑战性：需要战术思考才能突破
→ 叙事性：体现Militech的军事化管理
```

## 六、关键设计决策（Design Decisions）

### 决策1：为什么采用三层架构？

```
❓ 问题：
  能否只用一层系统（如：只用Squad）管理所有AI？

💡 答案：NO

理由1：职责分离
├── AttitudeGroup：全局派系关系（影响整个游戏）
├── Squad：战术协同单位（影响场景战斗）
└── Community：场景生命周期（影响NPC生成）
  → 三者职责完全不同，不应混为一谈

理由2：扩展性
├── 新增派系：只修改AttitudeGroup，不影响Squad
├── 新增战术：只扩展Squad，不影响Community
└── 新增场景：只创建Community，不影响派系关系

理由3：性能
├── AttitudeGroup：查询O(1)（HashMap）
├── Squad：只在有成员时存在
└── Community：流式加载，按需激活
  → 分层后每层可独立优化

结论：
三层架构是必须的，它保证了系统的可维护性、可扩展性和性能。
```

### 决策2：为什么Squad是独立系统？

```
❓ 问题：
  Squad能否作为CommunitySystem的一部分？

💡 答案：NO

理由1：Squad的生命周期独立于Community
├── Community卸载后，Squad可能仍然存在
├── 例：跟随玩家的Follower Squad
└── Squad需要独立的生命周期管理

理由2：Squad跨Community共享
├── Global Squad：跨多个Community
├── Attitude Squad：全游戏范围
└── 如果绑定到Community，无法跨场景

理由3：战术系统复杂度
├── CombatSquad有独立的战术系统
├── InfluenceMap、Reachability等子系统
└── 作为独立系统更易维护

结论：
SquadManager必须是独立的IGameSystem，
与CommunitySystem解耦。
```

### 决策3：为什么行为树共享而不是复制？

```
❓ 问题：
  每个NPC能否有独立的.behavior文件？

💡 答案：技术上可以，但不应该

理由1：内存优化
├── 100个守卫 × 1MB .behavior文件 = 100MB
├── 100个守卫共享1个.behavior文件 = 1MB
└── 节省99MB内存（99%优化）

理由2：设计一致性
├── 同一类型NPC应该有相同的行为逻辑
├── 例：所有Militech士兵应该用相同的战术
└── 共享保证一致性

理由3：迭代效率
├── 修改一个.behavior文件 → 所有NPC生效
├── 无需逐个修改
└── 大幅提升迭代效率

实现方案：
├── .behavior文件：共享（只读）
├── BehaviorTreeInstance：独立（运行时状态）
└── 达到内存优化 + 状态独立

结论：
行为树共享是正确的设计，
节省内存同时保证设计一致性。
```
