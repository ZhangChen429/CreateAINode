### 1.1 动态环境下的空间决策困境

**问题场景：**
- 战斗 AI：敌人应该躲在哪个掩体后？→ 掩体会被破坏
- 巡逻 AI：NPC 下一个巡逻点在哪？→ 关卡会调整
- 群体 AI：100 个单位如何散开？→ 环境动态变化

**传统方案的失效：**
- 手动放置点 → 环境改变后失效
- 硬编码路径 → 关卡调整后需改代码
- 预计算位置 → 无法应对动态场景

### 1.2 运行时推理 vs 预计算的权衡

| 维度 | 预计算（传统） | 运行时推理（EQS） | EQS 的选择 |
|------|--------------|-----------------|-----------|
| **灵活性** | ❌ 环境变化要重算 | ✅ 自动适应 | 牺牲性能换灵活性 |
| **性能** | ✅ 查表即可 | ⚠️ 每次计算 | 通过优化缓解 |
| **维护性** | ❌ 硬编码难改 | ✅ 配置化 | 关键优势 |
| **适用场景** | 静态世界 | 动态世界 | 现代游戏的刚需 |

### 1.3 与其他方案的对比优势

| 方案 | 核心问题 | EQS 的优势 |
|------|---------|-----------|
| **硬编码位置** | 不适应动态世界 | 运行时推理 |
| **预计算导航网格** | 内存爆炸 + 无法表达相对性 | 按需计算 + Context 参考系 |
| **Utility AI** | 候选生成与评分耦合 | Generator/Test 分离 |
| **机器学习** | 策划无法调参 | 配置化 + 可解释 |

    ├─ 2.2 四大组件的职责分离

### 2.1 核心理念：从"知道答案"到"知道标准"

```
传统方式：AI 知道答案在哪
  if (距离 < 10m && 有掩体) goto A点

EQS 方式：AI 知道评估标准
  Generator: 生成候选点
  Test1: 距离评分
  Test2: 掩体评分
  Finalize: 选最高分
```

**优势：**
- 答案可以动态变化（环境破坏后自动找新点）
- 标准可以配置调整（策划改权重）
- 逻辑可以复用（同一套 Test 用于多种查询）

### 2.2 四大组件的职责分离

| 组件 | 职责 | 类比 | 可配置性 |
|------|------|------|---------|
| **Generator** | 从哪里找候选 | 候选人海选 | ✅ 策划可配置范围 |
| **Test** | 如何评价候选 | 面试评分标准 | ✅ 策划可配置权重 |
| **Context** | 相对于什么评价 | 参考系 | ✅ 策划可选择对象 |
| **ItemType** | 候选项是什么类型 | 数据格式 | ⚠️ 程序员扩展 |

**分离的好处：**
- Generator 改了不影响 Test（改采样范围不改评分逻辑）
- Test 改了不影响 Generator（改权重不改候选生成）
- 新增 Context 不需要改 Test（多个威胁对象）

### 2.3 评分机制：归一化 + 加权求和

```
步骤1：各 Test 独立打分
  Test1(距离): 22米 → 原始分
  Test2(高度): 1.2米 → 原始分
  Test3(掩护): true → 原始分

步骤2：归一化到 [0, 1]
  Test1: 0.78
  Test2: 0.60
  Test3: 1.0

步骤3：加权求和
  最终分 = 0.78×0.5 + 0.60×0.2 + 1.0×0.3 = 0.81
```

**设计优势：**
- 不同量纲统一（米、角度、布尔值 → 标准分）
- 策划可调权重（强化某个维度的重要性）
- 算法固定简单（不需要复杂的决策树）

### 2.4 五大性能优化手段

| 优化手段 | 触发时机 | 效果 | 量化 |
|---------|---------|------|------|
| **按需触发** | 目标失效时才查询 | 不是每帧运行 | 触发频率：2-5秒/次 |
| **Generator 剔除** | 生成阶段过滤 | 减少候选数 | 1000候选 → 200候选 |
| **Test 淘汰** | 评分阶段提前过滤 | 减少计算量 | 200×5=1000 → 300次 |
| **异步计算** | 跨帧执行 | 不阻塞主线程 | 单次耗时：0.5-2ms |
| **空间分区** | 大地图场景 | 减少候选数 | 10000候选 → 100候选 |

### 3.1 系统定位：空间决策评分框架

**命名解读：**
- "环境查询"：查询环境中的信息（位置、对象、方向）
- "系统"：标准化的流程和组件
- 本质：**从多个候选中，根据多维度标准，选出最优项**

**应用范围：**
- ✅ 空间决策（找掩体、找集合点）
- ✅ 目标选择（选攻击目标、选拾取道具）
- ✅ 方向决策（选逃跑方向、选攻击角度）
- 🔮 未来：武器选择、技能选择、战术规划

### 3.2 架构分层：四层架构

```
┌────────────────────────────────────┐
│ 层级1：查询定义层                   │  ← 策划操作
│ Query Asset 配置                   │
├────────────────────────────────────┤
│ 层级2：执行调度层                   │  ← 引擎管理
│ Manager 调度 + 缓存 + 优先级        │
├────────────────────────────────────┤
│ 层级3：核心计算层                   │  ← 标准流程
│ Generate → Test → Finalize         │
├────────────────────────────────────┤
│ 层级4：扩展组件层                   │  ← 程序员扩展
│ 自定义 Generator/Test/Context      │
└────────────────────────────────────┘
```

**分层价值：**
- 层级1：降低使用门槛（策划无需编程）
- 层级2：保证系统性能（异步、缓存、优先级）
- 层级3：保证逻辑一致性（标准化流程）
- 层级4：保证扩展性（插件化组件）

### 3.3 扩展能力：从空间查询到通用决策

**通过 ItemType 扩展应用边界：**

| 阶段 | ItemType | 应用场景 | 覆盖率 |
|------|----------|---------|--------|
| **当前（内置）** | Point | 空间位置查询 | 90% |
| **当前（内置）** | Actor | 目标对象选择 | 8% |
| **当前（内置）** | Direction | 方向决策 | 2% |
| **未来（自定义）** | Weapon | 武器选择 | 扩展场景 |
| **未来（自定义）** | Skill | 技能选择 | 扩展场景 |
| **未来（自定义）** | Strategy | 战术规划 | 扩展场景 |

**意义：**
```
EQS = 通用的"多候选评估框架"
  ├─ 输入：候选集合（位置/对象/方向/...）
  ├─ 处理：多维度评分 + 加权选择
  └─ 输出：最优候选
```

## 📊 第三层：关键细节支撑

### Generator 职责边界的细节

| 层级 | 职责 | 示例 | Generator 是否负责 |
|------|------|------|-------------------|
| **引擎层语义** | 空间属性、基础类型 | "可导航区域""带标签的 Actor" | ✅ 负责 |
| **业务层语义** | 场景化决策逻辑 | "适合 AI 体型""能遮挡视野" | ❌ 交给 Test |

**为什么这样划分？**
- Generator 保持通用性 → 可复用于多种场景
- Test 承载业务逻辑 → 灵活配置权重
- 改需求只需调整 Test → 不需要改 Generator 代码

### Test 粒度选择的细节

**细粒度方案（EQS 选择）：**
```
狙击位置评估：
  Test1: Distance to Player (距离)
  Test2: Height Difference (高度)
  Test3: Line of Sight (视线)
  Test4: Cover from Behind (掩护)
```

**粗粒度方案（不推荐）：**
```
狙击位置评估：
  Test: Sniper Position Score (一个复杂 Test 搞定)
```

**为什么选细粒度？**
- ✅ 灵活：改高度权重不影响距离评分
- ✅ 可复用：Distance Test 可用于多种查询
- ✅ 可配置：策划可单独调整每个维度的权重
- ❌ 配置复杂：需要配置多个 Test（但换来灵活性）

### Context 多对象处理的细节

**场景：AI 要找位置，同时考虑多个威胁**

**模式1：多 Context → 多 Test（推荐）**
```
Test1: Distance to Player (权重0.3)
Test2: Distance to Enemy1 (权重0.3)
Test3: Distance to Enemy2 (权重0.2)

优势：每个威胁可以设置不同权重
```

**模式2：多 Context → 1 个 Test（轻量）**
```
Test: Distance
  Context: [Player, Enemy1, Enemy2]
  聚合规则：Minimum（到最近威胁的距离）

优势：配置简单，但无法差异化权重
```

**选择建议：**
- 重要决策 → 用模式1（精细控制）
- 次要决策 → 用模式2（简化配置）

### ItemType 内存布局的细节

**分离存储设计：**

```
Items[] (元数据)          RawData[] (实际数据)
┌────────────┐            ┌─────────┐
│Item[0]     │            │ FVector │
│Score: 0.8  │───────────>│(12字节) │
│RawPtr ─────┘            └─────────┘
│            │            ┌─────────┐
│Item[1]     │            │ FVector │
│Score: 0.6  │───────────>│(12字节) │
│RawPtr ─────┘            └─────────┘
└────────────┘
```

**为什么分离？**
1. **类型无关性**：Items[] 结构固定，无论 RawData 是什么类型
2. **内存连续性**：RawData[] 连续分配，CPU 缓存友好
3. **延迟绑定**：运行时才确定 ItemType，编译期不需要知道
