# ExecutionStream 在 AI 时代的迭代思考

## 一、当前系统的核心复杂性分析

**ExecutionStream 架构（2018-2019设计）：**

```text
┌─────────────────────────────────────────────────────────┐
│                    ExecutionStream                      │
├─────────────────────────────────────────────────────────┤
│  ActionChannel    ControlChannel   StimulationChannel  │
│  ├ ActionRecord[]    ├ Request[]       ├ StimulationRecord[]│
│  ├ m_indexed          ├ m_indexed       ├ m_indexed         │
│  ├ Reindex()          ├ Reindex()       ├ Reindex()         │
│  └ TimeWindow迭代      └ TimeWindow迭代     └ TimeWindow迭代    │
└─────────────────────────────────────────────────────────┘

```

**复杂性来源：**

1. **精确时序控制** - 设计师需手动指定毫秒级时间点 (5000ms, 10000ms...)
2. **三通道分离** - Action/Control/Stimulation 需要理解各自职责并手动协调
3. **索引机制** - 每次修改需要 `Reindex()`，设计师需理解索引状态
4. **Record 编码** - UserData、RecordType、Recordset 等复杂数据结构
5. **时间窗口计算** - TimeWindow 的手动设置和边界处理

## 二、 AI 时代的产品愿景

### 2.1 从"精确时序"到"意图表达"

**传统模式（当前）：**

> 设计师脑中："让V和Hanako在餐厅对话，Hanako先坐，V随后坐"
> ↓ 必须翻译为：
> Time 0ms: ChangeWorkEvent(Hanako, chair1)
> Time 2000ms: ChangeWorkEvent(V, chair2)
> Time 5000ms: WaitSignal(BothSeated)
> Time 6000ms: DialogLineEvent(Hanako, "...")
> ↓ 问题：
> * 如果动画时长改变？需要手动调整所有时间点
> * 如果增加一个角色？整个时序重排
> * 如果想要"自然感觉"？不知道该用多少毫秒
> 
> 

**AI时代模式：**

> 设计师输入（自然语言/结构化意图）：
> "让V和Hanako在餐厅对话"
> "Hanako优雅地先入座"
> "V等Hanako坐定后再坐"
> "双方都坐好后开始对话"
> ↓ AI 理解并生成 IntentStream：
> Intent[0]: Hanako sits (style: elegant)
> Intent[1]: V sits (trigger: after Hanako seated)
> Intent[2]: Dialog starts (trigger: both seated)
> ↓ 引擎自动计算：
> * 动画时长 → 自动推导时间点
> * 依赖关系 → 自动同步
> * 风格参数 → 选择合适的动画变体
> 
>

## 三、核心技术变革点

### 3.1 用 AI 替代手动时序

```cpp
// 当前：设计师必须理解这些
ActionRecord record;
record.m_executionPlan.m_startTime = Msec(5000);  // 为什么是5000？
record.m_executionPlan.m_conclusionTime = Msec(10000);  // 怎么算出来的？

// AI时代：设计师只需表达意图
Intent intent = {
    .action = "sit_down",
    .actor = hanako,
    .style = "elegant",  // AI选择合适动画
    .trigger = After(previous_intent)  // 自动计算时间
};
// AI自动计算: 动画时长3.2秒 + 自然间隔0.5秒 → startTime = prev.end + 500ms

```

### 3.2 用上下文推理替代权重配置

```cpp
// 当前：手动配置Selector权重
Selector {
    m_weights = [20, 30, 50],  // 设计师如何决定这些数字？
    m_list = [
        AnimClip { "sit_idle" },
        AnimClip { "sit_fidget" },
        AnimClip { "sit_wipe_forehead" }
    ]
}

// AI时代：上下文驱动的行为选择
BehaviorSelector {
    context = scene.GetEmotionalContext(),  // AI分析当前情境
    // LLM在运行时决定："考虑到刚才的紧张对话，NPC应该表现出不安"
    // 自动选择fidget或wipe_forehead
}

```

### 3.3 三通道统一为意图层

```text

        { type: Action, ... },

    ],
    // AI自动处理：
    // - 依赖推断
    // - 冲突解决
    // - 时序优化
}

```

## 五、具体实施建议

### Phase 1: AI 辅助工具（3-6个月）

**目标：** 不改变现有架构，在上层增加 AI 辅助

1. **Scene Description Parser**: 输入自然语言场景描述，输出结构化Intent列表（实现：LLM + 游戏域知识）。
2. **Timeline Auto-Scheduler**: 输入Intent列表 + 动画库，输出精确的ExecutionStream配置（实现：约束求解 + 动画时长数据库）。
3. **Emotional Context Injector**: 输入场景剧本 + 角色关系，输出Workspot的context参数（实现：情感分析模型）。
4. **AI Validator**: 自动检测冲突、不自然的时序，输出修复建议或自动修正。

### Phase 2: 核心重构（6-12个月）

**目标：** 简化底层，移除不必要的复杂性

1. **合并三通道为IntentStream**: 移除设计师可见的 Action/Control/Stimulation 区分。
2. **移除手动索引**: 实现自动增量索引，对外无感知。
3. **相对时序替代绝对时序**: 使用 `After(hanako.seated)` 替代 `Msec(5000)`。
4. **声明式替代命令式**: 使用 `State { actors: [...] }` 替代 `StoreActionRecord(...)`。

### Phase 3: 生成式叙事（12-24个月）

**目标：** AI 可以根据高层目标生成完整场景

1. **对话生成**: 输入叙事目标，输出完整对话脚本 + 情感标注。
2. **行为编排**: 输入对话内容 + 角色性格，输出合适的Workspot选择和时序。
3. **分支预测**: 输入玩家历史行为模式，输出个性化的场景变体。
4. **实时调整**: 运行时根据玩家反应调整后续内容。

## 六、风险与权衡

**保留当前系统的理由：**

* ✅ **确定性**：精确时序保证一致性体验
* ✅ **可控性**：设计师完全掌控每个细节
* ✅ **可调试**：问题易于定位和修复
* ✅ **已验证**：数百个场景证明系统可靠

**AI系统的风险：**

* ⚠️ **不确定性**：AI生成可能"跑偏"
* ⚠️ **黑盒问题**：难以解释为什么选择某个动画
* ⚠️ **边界情况**：复杂场景可能生成失败
* ⚠️ **迭代成本**：AI模型需要持续训练和调优

**建议的平衡（混合模式）：**

```text
┌────────────────────────────────────────────────────────────┐
│                        混合模式                            │
│                                                            │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐     │
│  │  AI 生成    │ →  │  人工审核   │ →  │  精确执行   │     │
│  │  (草稿)      │    │  (调整)      │    │  (确定)      │     │
│  └─────────────┘    └─────────────┘    └─────────────┘     │
│                                                            │
│  - AI 负责繁琐的时序计算                                   │
│  - 人工保留创意决策权                                      │
│  - 底层仍使用确定性执行                                    │
└────────────────────────────────────────────────────────────┘

```

## 七、核心结论

ExecutionStream 在 AI 时代应该做的不是"消失"，而是**"下沉"**：

1. **对设计师隐藏**: 三通道、索引、毫秒时序这些实现细节不应暴露。
2. **对 AI 开放**: 成为 AI 编排系统的执行后端。
3. **保持确定性**: 运行时仍需精确可控的执行能力。
4. **增加可解释性**: AI 生成的结果需要能被人类理解和调整。

**最终愿景：**

> 叙事设计师 → 创意意图（自然语言）
> ↓
> AI Narrative Agent → 结构化场景（IntentStream）
> ↓
> AI Scheduler → 精确时序（隐藏的ExecutionStream）
> ↓
> 游戏引擎 → 沉浸式体验

这样既保留了系统的工程精华（精确执行、复用性、可扩展性），又让设计师从技术细节中解放出来，专注于讲好故事。
