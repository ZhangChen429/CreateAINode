# 非线性网状叙事的技术困难：从ExecutionStream视角
> 黄金圈结构解析：Why - How - What

---

## 🎯 概述

```
非线性网状叙事 = 玩家选择驱动的分支剧情

问题：
  线性叙事：A → B → C（确定的时间序列）
  非线性叙事：A → {B1, B2, B3} → {C1, C2, ...}（动态的网状结构）

核心矛盾：
  设计时：网状图（表达所有可能性）
  运行时：线性流（只执行一条路径）

ExecutionStream的角色：
  将网状图编译成可执行的时间流
  处理动态选择带来的时间不确定性
```

---

# 第一部分：WHY - 为什么会有这些困难？

## 1.1 根本原因：两个世界的冲突

```
┌─────────────────────────────────────────────────────────┐
│                    设计师的世界                          │
│                                                          │
│   思维模式：所有可能性同时存在                           │
│   表达方式：网状图（节点 + 连线）                        │
│   时间概念：相对的、模块化的                             │
│   关注点：剧情逻辑、分支合理性、玩家体验                 │
│                                                          │
└─────────────────────────────────────────────────────────┘
                          ↓ 冲突
┌─────────────────────────────────────────────────────────┐
│                    计算机的世界                          │
│                                                          │
│   执行模式：每时刻只能执行一条指令                       │
│   执行方式：时间序列（按时间顺序）                       │
│   时间概念：绝对的、连续的                               │
│   关注点：性能、确定性、实时响应                         │
│                                                          │
└─────────────────────────────────────────────────────────┘

根本矛盾：
  网状结构（2D+） ≠ 时间序列（1D）
  所有可能性 ≠ 单一执行路径
  相对时间 ≠ 绝对时间
```

---

## 1.2 为什么线性叙事没有这个问题？

```
线性叙事的简单性：

  设计时：A → B → C
  运行时：A → B → C

  一一对应，无需转换

  时间计算：
    A: 0-5s
    B: 5-10s
    C: 10-15s

  编译时就能确定所有时间点
  运行时直接按时间执行

非线性叙事的复杂性：

  设计时：
        ┌→ B1 → C1
    A → ├→ B2 → C2
        └→ B3 → C3

  运行时（玩家选择B2）：
    A → B2 → C2

  问题：
    1. 运行时才知道走哪条路
    2. 玩家选择的时间不确定
    3. 不同路径的时长可能不同
    4. 后续节点的时间依赖前面的选择
```

---

## 1.3 为什么时间是核心难点？

```
游戏的实时性要求：

  60fps = 每16.6ms需要回答：
    "现在应该执行什么？"
    "哪些动作要启动？"
    "哪些动作要结束？"

  这是时间查询，不是逻辑查询

网状结构不适合时间查询：

  查询："Time=5000ms执行什么？"

  网状结构的回答方式：
    1. 从起点遍历
    2. 累加每个节点的duration
    3. 判断5000ms在哪个节点
    4. 遍历该节点的Event

    复杂度：O(节点数)

  时间序列的回答方式：
    1. 二分查找5000ms

    复杂度：O(log n)

性能差异：
  100个节点 × 60fps = 每秒6000次遍历（网状）
  vs
  7次比较 × 60fps = 每秒420次比较（时间序列）

  14倍性能差距
```

# 第二部分：HOW - 如何解决这些困难？

## 2.1 核心策略：编译 + 动态合并

```
策略概述：

  ┌─────────────────┐
  │  SceneGraph     │ ← 设计时：网状结构
  │  (设计时核心)    │
  └────────┬────────┘
           │ 编译
           ↓
  ┌─────────────────┐
  │ ExecutionStream │ ← 运行时：时间序列
  │  (运行时核心)    │
  └─────────────────┘

编译解决：
  ✅ 相对时间 → 绝对时间
  ✅ 图遍历 → 时间排序
  ✅ O(n)查询 → O(log n)查询

动态合并解决：
  ✅ 分支的运行时选择
  ✅ 玩家选择时间的不确定性
  ✅ 路径的动态拼接
```

---

## 2.2 编译策略详解

### 策略1：分段编译

```
不是一次编译整个图，而是分段：

  [确定段] → [选择点] → [分支段1]
                      → [分支段2]
                      → [分支段3]

编译规则：
  1. 确定段：直接编译成绝对时间
  2. 选择点：标记为"等待"
  3. 分支段：独立编译，时间从0开始

示例：

  SceneGraph：
    Section_A (5s) → ChoiceNode → Branch_B1 (3s)
                                → Branch_B2 (4s)

  编译结果：
    mainStream: [0-5s的Event] + [ChoiceNode标记]
    branchB1Stream: [0-3s的Event]（相对时间）
    branchB2Stream: [0-4s的Event]（相对时间）
```

### 策略2：预编译所有分支

```
为什么预编译？

  运行时编译 = 卡顿（2-5ms）
  预编译 = 平滑（合并只需<1ms）

预编译范围：
  ✅ 所有可能的分支
  ✅ 所有选择的后续路径
  ✅ 甚至嵌套的分支

代价：
  内存增加（存储多个流）
  加载时间增加（编译所有分支）

收益：
  运行时无卡顿
  玩家体验流畅
```

### 策略3：延迟确定绝对时间

```
核心洞察：

  分支的"内部相对时间"是确定的
  分支的"全局绝对时间"是运行时才知道的

因此：
  编译时：计算分支内部的相对时间
  运行时：加上偏移量得到绝对时间

公式：
  绝对时间 = 分支相对时间 + 玩家选择时刻

示例：
  Branch_B1内部：
    Event_1 @ 0ms（相对）
    Event_2 @ 1000ms（相对）

  玩家在12000ms选择B1：
    Event_1 @ 12000ms（绝对）
    Event_2 @ 13000ms（绝对）
```

## 2.3 动态合并策略详解

### CombineSubstream机制

```cpp
// ExecutionStream的核心方法
void CombineSubstream(
    const ExecutionStream& branchStream,  // 预编译的分支流
    Uint32 offsetMsec                      // 偏移量 = 当前时间
);

// 合并逻辑（伪代码）
void CombineSubstream(branchStream, offset) {
    for (record in branchStream.actionChannel) {
        // 核心：加上偏移量
        record.absoluteTime = record.relativeTime + offset;

        // 添加到主流
        this.actionChannel.append(record);
    }

    // 重新排序
    this.Reindex();
}
```

### 合并时机

```
触发合并的时刻：

  1. ChoiceNode：玩家做出选择
     → 合并选择的分支流

  2. 条件分支：条件满足
     → 合并对应的分支流

  3. 并行汇聚：所有分支完成
     → 合并后续流

合并的实时性要求：
  必须在1帧内完成（<16.6ms）
  实际：<1ms（只是数组操作）
```

## 2.4 处理特殊情况

### 情况1：并行分支

```
问题：
  A → [B1, B2] → C（并行执行B1和B2，都完成后执行C）

  B1: 3秒
  B2: 5秒

  C何时开始？max(3, 5) = 5秒

解决：
  编译时：记录"C依赖B1和B2"
  运行时：跟踪B1和B2的完成状态
          两者都完成后，合并C的流

  实现：
    HubNode（AndNode）：等待所有输入信号
    收到所有信号后：触发后续流的合并
```

### 情况2：循环

```
问题：
  A → [Loop: B] → C（B循环执行N次，N运行时确定）

  B: 2秒/次
  循环次数：？

解决方案1：展开循环（如果次数有上限）
  编译时：展开maxLoop次
  运行时：提前退出

解决方案2：动态生成
  每次循环完成：
    检查退出条件
    如果继续：合并下一次B的流
    如果退出：合并C的流

CDPR可能的选择：
  方案2（动态生成）
  因为循环次数真的不确定
```

### 情况3：嵌套选择

```
问题：
  A → Choice1 → [B1 → Choice2 → [C1, C2],
                 B2 → Choice3 → [D1, D2]]

  两层嵌套选择，4种最终路径

解决：
  递归预编译所有路径：
    mainStream: A → Choice1
    branch_B1: B1 → Choice2
    branch_B1_C1: C1...
    branch_B1_C2: C2...
    branch_B2: B2 → Choice3
    branch_B2_D1: D1...
    branch_B2_D2: D2...

  运行时依次合并：
    玩家选择B1 → 合并branch_B1
    玩家选择C2 → 合并branch_B1_C2
```

## 3.2 解决方案清单

### 问题1：相对时间无法直接执行

```
问题：
  Event在SectionNode内的时间是相对的
  运行时需要绝对时间

解决方案：编译时累加转换

  输入：
    Section_A.Event_1 @ 0ms（相对）
    Section_A.Event_2 @ 2000ms（相对）
    Section_A.duration = 5000ms
    Section_B.Event_3 @ 0ms（相对）

  编译：
    currentTime = 0
    Event_1: 0 + 0 = 0ms（绝对）
    Event_2: 0 + 2000 = 2000ms（绝对）
    currentTime += 5000
    Event_3: 5000 + 0 = 5000ms（绝对）

  输出：
    [0ms]: Event_1
    [2000ms]: Event_2
    [5000ms]: Event_3
```

### 问题2：图遍历查询慢

```
问题：
  每帧需要查询"Time=X时执行什么"
  图遍历 = O(n)

解决方案：编译成时间排序数组

  编译后：
    ActionChannel = [
      {time: 0, event: E1},
      {time: 2000, event: E2},
      {time: 5000, event: E3},
      ...
    ]  // 已按时间排序

  查询：
    二分查找Time=5000 → 直接定位
    复杂度：O(log n)
```

### 问题3：玩家选择时间不确定

```
问题：
  ChoiceNode等待玩家选择
  选择时间 = 1秒？30秒？

解决方案：分支独立编译 + 运行时偏移合并

  编译时：
    mainStream: 到ChoiceNode为止
    branchStream: 从0开始的相对时间

  运行时（玩家在T=12s选择）：
    CombineSubstream(branchStream, 12000)

    分支Event的绝对时间 = 相对时间 + 12000
```

### 问题4：分支路径运行时才确定

```
问题：
  3个分支，只执行1个
  编译时不知道执行哪个

解决方案：预编译所有分支

  编译时：
    branch_A_Stream（预编译）
    branch_B_Stream（预编译）
    branch_C_Stream（预编译）

  运行时：
    玩家选择B → 只合并branch_B_Stream
    其他两个流丢弃（或保留用于回溯）
```

### 问题5：并行分支的汇聚时间

```
问题：
  A → [B1(3s), B2(5s)] → C
  C的开始时间 = A结束时间 + max(3, 5)

解决方案：HubNode信号等待

  设计：
    HubNode（AndNode）等待所有输入信号

  运行时：
    B1完成 → 发送Signal → HubNode收到1/2
    B2完成 → 发送Signal → HubNode收到2/2
    HubNode触发 → 合并C的流，偏移量 = 当前时间
```

### 问题6：循环次数不确定

```
问题：
  Loop节点执行N次，N运行时确定

解决方案：每次循环动态合并

  编译时：
    loopBodyStream（循环体，从0开始）
    afterLoopStream（循环后，从0开始）

  运行时：
    每次循环完成：
      检查退出条件
      if 继续: CombineSubstream(loopBodyStream, currentTime)
      if 退出: CombineSubstream(afterLoopStream, currentTime)
```

### 问题7：嵌套选择的组合爆炸

```
问题：
  3层选择，每层3个选项 = 3^3 = 27条路径

解决方案：层级预编译

  不是编译27条完整路径
  而是编译每一层的分支：
    Layer1: 3个分支流
    Layer2: 3个分支流（每个Layer1分支内）
    Layer3: 3个分支流（每个Layer2分支内）

  运行时逐层合并：
    玩家选择Layer1.B → 合并Layer1.B流
    玩家选择Layer2.A → 合并Layer2.A流
    玩家选择Layer3.C → 合并Layer3.C流

  存储：3 + 3 + 3 = 9个分支流（而不是27条路径）
```

### 问题8：中断和恢复

```
问题：
  对话中战斗爆发 → 中断Scene
  战斗结束 → 恢复Scene

解决方案：状态快照 + 重定位

  中断时：
    保存currentTime
    保存当前执行的Event
    保存Actor状态

  恢复时：
    恢复Actor状态
    从currentTime继续执行
    或从某个Checkpoint重新开始

  ExecutionStream支持：
    任意时间点开始执行（只需设置currentTime）
    无需重新遍历图
```

### 问题9：快进和回退

```
问题：
  玩家想跳过对话 → 快进
  玩家想重看 → 回退

解决方案：时间跳转

  快进：
    currentTime += skipAmount
    查询新时间点的Event
    跳过中间的Event或快速执行

  回退（如果支持）：
    currentTime -= rewindAmount
    需要保存历史状态
    或从Checkpoint重放

  ExecutionStream的优势：
    时间排序 → 任意时间点定位 = O(log n)
    无需重新执行整个图
```

### 问题10：调试和观察

```
问题：
  运行时看不到"当前在哪个节点"
  ExecutionStream丢失了节点边界信息

解决方案：保留调试信息

  编译时：
    ActionRecord.debugInfo = {
      sourceNode: "SectionNode_Greeting",
      sourceEvent: "DialogLine_01",
      sourceLine: 42  // 设计文件行号
    }

  运行时调试器：
    显示当前执行的ActionRecord
    反查sourceNode → 高亮SceneGraph中的节点
    显示当前时间 / 总时长
    显示已执行 / 待执行的Event数量
```

## 3.3 ExecutionStream的三通道设计

```
针对不同类型的困难，ExecutionStream设计了三个通道：

┌─────────────────────────────────────────────────────────┐
│                   ExecutionStream                        │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  ┌─────────────────────────────────────────────────┐    │
│  │ ActionChannel（动作通道）                        │    │
│  │                                                  │    │
│  │ 解决问题：                                       │    │
│  │   ✅ 相对时间 → 绝对时间                        │    │
│  │   ✅ 时间排序 → 快速查询                        │    │
│  │   ✅ 时间窗口查询                               │    │
│  │                                                  │    │
│  │ 存储：按时间排序的ActionRecord数组              │    │
│  └─────────────────────────────────────────────────┘    │
│                                                          │
│  ┌─────────────────────────────────────────────────┐    │
│  │ ControlChannel（控制通道）                       │    │
│  │                                                  │    │
│  │ 解决问题：                                       │    │
│  │   ✅ 分支选择 → 取消未选分支                    │    │
│  │   ✅ 中断处理 → 取消当前动作                    │    │
│  │   ✅ 循环控制 → 提前退出                        │    │
│  │                                                  │    │
│  │ 存储：取消请求队列                              │    │
│  └─────────────────────────────────────────────────┘    │
│                                                          │
│  ┌─────────────────────────────────────────────────┐    │
│  │ StimulationChannel（刺激通道）                   │    │
│  │                                                  │    │
│  │ 解决问题：                                       │    │
│  │   ✅ 预加载资源 → 避免卡顿                      │    │
│  │   ✅ 提前通知系统 → 平滑过渡                    │    │
│  │   ✅ 预测即将发生的事件                         │    │
│  │                                                  │    │
│  │ 存储：预告通知队列                              │    │
│  └─────────────────────────────────────────────────┘    │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

## 3.6 总结

```
非线性网状叙事的核心困难：

  WHY：
    网状设计 ≠ 线性执行
    相对时间 ≠ 绝对时间
    所有可能 ≠ 单一路径
    动态选择 ≠ 静态编译

  HOW：
    分段编译（确定段 + 分支段）
    预编译所有分支
    运行时动态合并
    三通道设计（Action/Control/Stimulation）

  WHAT：
    10个具体问题 + 10个解决方案
    编译器：相对→绝对，图→流
    CombineSubstream：动态合并分支
    三通道：分离关注点

ExecutionStream的价值：
  ✅ 解决时间不确定性
  ✅ 解决路径动态性
  ✅ 保证运行时性能
  ✅ 支持复杂的非线性叙事
```
